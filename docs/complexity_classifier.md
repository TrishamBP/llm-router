# Complexity Classifier (Fireworks embeddings → CPU classifier)

The first router component: predict whether a prompt is `easy`, `medium`, or `hard`.
Prompts are embedded with a Fireworks.ai embeddings model (OpenAI-compatible API), and a
lightweight classifier is trained on the cached vectors on CPU. No language model is trained.

## Pipeline and methodology

1. **Download.** Byte-identical originals go to `data/raw/brick-complexity-extractor/<revision>/`,
   along with `provenance.json`: SHA-256 of each file, license, time, and content fingerprint
   `dd9d0b82337a2f1c`. Hashes are re-verified on every load, and raw files are never modified.
2. **Preprocessing** (`data/processed/brick-complexity/`):
   - Text normalisation is conservative: NFC, CRLF → LF, control and zero-width characters
     removed, trailing spaces trimmed, 3+ blank lines collapsed. Indentation, internal spacing,
     and all symbols are kept.
   - Labels must be one of `easy` / `medium` / `hard`.
   - Queries are grouped by an aggressive key (NFKC, case-folded, whitespace collapsed, edge
     punctuation stripped). Same-label duplicates keep one row and record the others' IDs;
     groups with conflicting labels are dropped (configurable).
   - All official splits are pooled and **re-split 80/10/10**, stratified by label at group
     level, so near-identical queries can't leak across splits. Isolation is checked and
     recorded in `manifest.json`, and embedding generation refuses to run without it.
   - Every row keeps its source ID (`<official split>-<index>`), original label, and source split.
     Every removal is listed in `removed.jsonl` with a reason.
   - Result: 76,831 in, 76,825 out (6 duplicates removed). **61,461 / 7,682 / 7,682** rows, with
     the class ratio held in each split. Processed fingerprint `080d9093d1041fa5`.
3. **Embeddings.** Batches go to Fireworks with a client-side rate limit. 429s, timeouts,
   connection errors, and 5xx are retried with bounded exponential backoff and full jitter,
   honouring `Retry-After`. Auth (401/403), unknown model (404), and rejected requests
   (400/422) are never retried. A rejected batch is bisected until the offending inputs are
   isolated, and they're recorded as failed examples.
4. **Training.** Standardised features, then multinomial logistic regression (grid
   `C ∈ {0.01, 0.1, 1, 10}` × `class_weight ∈ {none, balanced}`). Linear SVM is optional
   (`C ∈ {0.01, 0.1, 1}`). Fits use the training split only, and the model is picked by
   validation macro-F1, with validation hard recall breaking ties. Calibration is also checked
   on validation (log loss, Brier, top-class ECE). The test split is never loaded during
   training (a unit test checks this). XGBoost and an MLP are compared against this
   baseline; see [XGBoost and MLP classifiers](#xgboost-and-mlp-classifiers).
5. **Evaluation.** One pass on test, using cached embeddings and no API calls. Reports:
   - accuracy, macro and weighted F1, per-class precision/recall/F1, confusion matrix;
   - hard recall and **hard → easy misroutes**, which matter most for routing;
   - top-probability distributions;
   - local classification latency (median and p95), plus training and embedding durations.
6. **Inference.** `ComplexityRouter` applies the same normalisation, embeds with the
   configured model, checks that the model ID and dimension match the training metadata,
   and classifies.

## Setup

Dependencies are managed with uv only (no pip, no `requirements.txt`).

```bash
# Linux / macOS
uv sync --group complexity
cp .env.example .env          # then edit .env: FIREWORKS_API_KEY, FIREWORKS_EMBEDDING_MODEL
```

```powershell
# Windows PowerShell
uv sync --group complexity
Copy-Item .env.example .env   # then edit .env: FIREWORKS_API_KEY, FIREWORKS_EMBEDDING_MODEL
```

`.env` is git-ignored. The key is read only when an API call is about to be made. It is
never printed, logged, stored in artifacts, or included in error messages.

`FIREWORKS_EMBEDDING_MODEL` has **no default**. Choose an embeddings model in Fireworks' model
library and paste its exact ID. If the connectivity test fails with a 404 or a malformed
response, the model is wrong or doesn't serve embeddings. The pipeline reports this and never
switches to another model.

## Caching and resuming

- Embeddings are stored in `artifacts/embeddings/<cache_key>/`. The key hashes the processed
  fingerprint, preprocessing version, model ID, and `dimensions` setting, so one directory
  always holds exactly one model's vectors.
- Each finished batch is written atomically to `parts/<split>/<batch>.npz` and `state.json`
  is updated. If the job stops (Ctrl-C, network loss, rate-limit exhaustion), re-run the same
  command and finished batches are skipped. Keep `batch_size` unchanged when resuming; the job
  refuses to resume if it changes.
- Finished splits become `<split>.npy` plus `<split>.row_mapping.jsonl` (row, `example_id`,
  label, query hash), and `metadata.json` holds model, dimension, fingerprints, usage, and
  timings. `artifacts/embeddings/latest.json` points training at the latest complete cache.
- The connectivity result is in `artifacts/embeddings/connectivity/`. The full job requires a
  successful test **for the same model** first.

## Cost and runtime

- The full job is **1,203 requests and 26.6M characters** (train 961 / validation 121 /
  test 121 requests at batch size 64). The client-side limit of 60 requests/min means at least
  about 20 minutes, plus latency.
- No price is hardcoded. To get estimates, set `embeddings.price_per_million_tokens` from
  Fireworks' pricing page for your chosen model, run a pilot (`--max-batches 5`), then `--plan`.
  The plan extrapolates tokens per character from the token usage Fireworks reported for the
  pilot. Real usage and an estimate from reported tokens are written to `metadata.json`.
- Training and evaluation run on CPU with scikit-learn. With 61k rows × d dimensions, logistic
  regression takes minutes on a laptop. Runtime grows with the embedding dimension.

## XGBoost and MLP classifiers

Two more CPU classifiers use the same cached embeddings, the same 80/10/10 splits, and the same
selection rule as the baseline: validation macro-F1, with validation hard recall as the tie-break.
Neither needs CUDA. Both are sized for an 8 GB RAM machine, but that's a design target; the
actual figures are the per-job peak RSS values written to the reports.

### Data flow

```text
data/processed/brick-complexity/<split>.jsonl ──┐ (example_id, label, query; hash-checked)
artifacts/embeddings/<key>/<split>.npy (mmap) ──┼─► FeatureMatrix ─► XGBoost / MLP ─► P(easy, medium, hard)
features/text_features.py (engineered, log1p) ──┘     (feature_schema.json saved with every model)

inference: query ─► normalize_text ─► Fireworks embedding (model ID + dimension checked)
                                   └► engineered features (definition hash checked) ─► same model
```

### Feature sets (ablation)

| Feature set | Columns |
|---|---|
| `embeddings` | the Fireworks vector, unchanged (`emb_0000` …) |
| `engineered` | 16 deterministic regex counts, then a fixed log1p |
| `embeddings+engineered` | both, in that order |

Engineered features (`features/text_features.py`, version `1`): `n_chars`, `n_words`, `n_tokens`
(regex tokenizer `\w+|[^\w\s]`, not the embedding model's tokenizer), `n_lines`,
`n_code_fences`, `n_inline_code`, `n_code_tokens` (keywords, operators, calls, lines ending
in `;{}`), `n_math_symbols`, `n_latex_commands`, `n_dollar_math`, `n_arithmetic_expressions`,
`n_question_marks`, `n_instruction_verbs` (fixed verb list), `n_list_items`, `n_json_keys`,
`n_table_rows`. They are computed from the normalised query only. Nothing comes from labels,
judge output, or confidence (the dataset has no confidence field). Every one is a heuristic, and
longer prompts are not assumed to be harder. The schema stores a hash of every pattern, and a
model whose hash differs from the current code is refused at load time.

### Experiments

| ID | Model | Inputs |
|---|---|---|
| A | logistic regression (baseline; reused if a compatible model exists) | embeddings |
| B | XGBoost | embeddings |
| C | MLP | embeddings |
| D | XGBoost | embeddings + engineered |
| E | MLP | embeddings + engineered |
| F1 / F2 | XGBoost / MLP (ablation) | engineered only |

For each family, the better of the embeddings and embeddings+engineered variants (by validation)
is copied to `artifacts/models/xgboost` and `artifacts/models/mlp`. Only after that are all
trained models evaluated on test, once. Smoke runs evaluate on validation and never read test.

### Models

- **XGBoost** (`training/train_xgboost.py`). This uses the native API, equivalent to
  `XGBClassifier(objective="multi:softprob", num_class=3, n_estimators=200, max_depth=4,
  learning_rate=0.05, subsample=0.8, colsample_bytree=0.7, tree_method="hist",
  eval_metric="mlogloss", n_jobs=2, random_state=42)`. Rows are streamed from the memory
  map into a `QuantileDMatrix` in 8,192-row chunks, so the float matrix is never copied whole.
  Early stopping uses validation mlogloss (20 rounds), and the saved booster is trimmed to its
  best iteration. These are starting values, not tuned optima. Validate them before relying
  on them.
- **MLP** (`training/train_mlp.py`, `models/complexity_mlp.py`). The network is
  `Linear(d,256) → ReLU → Dropout(0.2) → Linear(256,128) → ReLU → Dropout(0.1) → Linear(128,3)`.
  For 4096-d input that's 1,082,115 parameters (about 4.3 MB in float32). It trains with
  CrossEntropyLoss and AdamW (lr 1e-3, weight decay 0.01), batch 128, at most 30 epochs, and
  patience 5 on validation macro-F1. Inputs are standardised with a mean/std fitted on train
  only, saved as `standardizer.npz`. Python, NumPy, and torch are seeded, with
  `num_workers=0`, float32 throughout, and evaluation under `torch.no_grad()`. Only the best
  checkpoint is saved.
- **Class weighting.** `balanced` (n / (3·count), training counts only) is evaluated next to
  `none` only if the training max/min class ratio is at least `resources.imbalance_threshold`
  (2.0). The current split has 31,443 / 9,872 ≈ 3.2. The better setting by validation is kept,
  and both are recorded under `variants` in `metadata.json`.
- **Budgets.** One thread budget (`resources.threads`, default 2) covers BLAS, OpenMP,
  XGBoost, and torch. If time (`max_train_seconds`) or RSS (`memory_budget_gb`) is exceeded,
  training stops, keeps the best model so far, and records `status: stopped_by_budget`.
  XGBoost also refuses to start if its estimated quantised-data size exceeds the memory budget.

### Memory considerations (estimates, not measurements)

| Item | Size |
|---|---|
| Train embeddings, 61,461 × 4096 float32 (memory-mapped) | 1.01 GB |
| Validation / test embeddings | 0.13 GB each |
| XGBoost quantised train + validation (1 byte/bin at `max_bin` 256) | ≈ 0.28 GB |
| XGBoost chunk copies (8,192 × 4,112 float32) | ≈ 0.13 GB each |
| MLP weights + AdamW state | ≈ 0.02 GB |
| Baseline logistic regression (existing code: loads train fully, StandardScaler copy) | ≥ 2 GB |
| Near-duplicate audit (normalised val/test copy + one similarity block) | ≈ 0.25 GB |

Touched memory-map pages count toward RSS, so reported peaks include up to about 1 GB of
reclaimable file cache. Peak RSS is measured per job (each runs in its own process) and
written to `metadata.json → resources` and `comparison.md`.

### Running on Lightning AI

`data/` and `artifacts/` are git-ignored, and this folder isn't a git repository, so copy them
over explicitly. Leave out `.venv/` and `.env`, which training doesn't need. Wait until the
embedding job has finished (`artifacts/embeddings/<key>/metadata.json` shows `"complete": true`
and `{train,validation,test}.npy` exist). The `parts/` subfolder isn't needed for training.

```bash
# from your machine, in the repository root (example using rsync over SSH)
rsync -av --exclude .venv --exclude .env --exclude 'artifacts/embeddings/*/parts' \
    ./ <studio-ssh-host>:~/llm_router/

# on the Studio
cd ~/llm_router
bash scripts/setup_lightning_complexity.sh          # uv sync --group complexity + checks + smoke
uv run python -m llm_router.training.run_comparison # full comparison (sequential jobs)
```

On Linux, `uv sync` installs the default PyPI torch wheel, which includes CUDA libraries. It
works on CPU-only Studios, just with a larger download. The classifiers never move anything to
a GPU.

Individual jobs:

```bash
uv run python -m llm_router.training.train_xgboost --smoke
uv run python -m llm_router.training.train_xgboost --feature-set embeddings+engineered
uv run python -m llm_router.training.train_mlp --feature-set embeddings --lr 1e-3 --batch-size 128
uv run python -m llm_router.training.evaluate_classifiers --model-dirs artifacts/models/xgboost artifacts/models/mlp
uv run python -m llm_router.training.run_comparison --only B C --baseline skip --threads 4 --max-seconds 7200
uv run pytest tests/unit/complexity        # includes the torch tests once torch is installed
```

Common flags: `--threads`, `--max-seconds` (≤ 0 disables it), `--memory-budget-gb`, `--seed`,
`--feature-set`, `--output-name`, `--smoke`. On a larger Studio, raising `--threads`
shortens XGBoost training. Keep it at or below the vCPU count.

### Inference

```python
from llm_router.inference.classifier import ComplexityRouter

router = ComplexityRouter.from_pretrained("artifacts/models/mlp")
router.predict("Design a distributed scheduler that minimizes GPU idle time.").to_dict()
# {"label": ..., "probabilities": {"easy": ..., "medium": ..., "hard": ...},
#  "classifier": "mlp", "embedding_model": "fireworks/qwen3-embedding-8b"}

router = ComplexityRouter.from_config("configs/complexity.yaml")  # classifier.type / model_dir
```

`classifier.type` accepts `logistic_regression`, `xgboost`, or `mlp`. A configured type that
doesn't match the model directory is an error. Loading also refuses a missing or corrupt file,
an unknown classifier type, probability columns that aren't in `easy, medium, hard` order, a
schema/model feature-count mismatch, a changed engineered-feature definition, a different
embedding model, or a wrong embedding dimension. Engineered-only models don't call the
embedding API.

## Known limitations

- Labels come from an LLM judge (Qwen3.5-122B), not humans. The medium/hard boundary is
  subjective by the card's own account. Metrics measure agreement with that judge.
- With no confidence field, the "confidence filtering" experiment can't run on this revision.
  The code supports it (`preprocessing.min_confidence`) for datasets that include confidence.
- Near-duplicate detection is by normalised text only. Paraphrases with different wording are
  not grouped. The card states upstream MinHash deduplication (Jaccard 0.85).
- The 80/10/10 re-split means results aren't directly comparable with numbers reported on the
  official 85/10/5 splits.
- Logistic-regression probabilities aren't guaranteed to be calibrated. See the validation
  calibration metrics before using them as thresholds.
- The data is English only, and its topics reflect early-2026 queries.
- XGBoost and MLP use fixed starting configurations: early stopping and the class-weight
  choice are the only things selected on validation. There's no broader hyperparameter
  search, so results may be below what a tuned model would reach. Whether either beats
  logistic regression is an empirical question that the comparison report answers.
- XGBoost and MLP probabilities aren't calibrated either. Log loss, Brier score, and ECE are
  reported for validation and test.
- The embedding near-duplicate audit (cosine ≥ 0.98 to any training row) only reports. It
  doesn't change the splits. Test metrics excluding flagged rows are shown as a sensitivity
  check.
- Engineered features are regex heuristics: `n_tokens` approximates, but doesn't equal, the
  embedding model's token count, and code/math detection can misfire on prose.
